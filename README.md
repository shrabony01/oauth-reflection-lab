# OAuth 2.0 Security & UX Reflection (Authentication lab-3)
# 1. CSRF and the state Parameter
In an OAuth flow, an attacker can perform a Cross-Site Request Forgery (CSRF) attack by starting the login process with their own third-party account (such as GitHub or Google), intercepting the callback URL containing their valid authorization code before it finishes redeeming, and tricking an authenticated victim into clicking that link. When the victim's browser visits the callback URL, the application exchanges the attacker's authorization code and links the attacker's third-party account to the victim's existing application account—allowing the attacker to later log into the victim's profile via OAuth. Using a cryptographically random, unguessable state parameter prevents this because the application binds the state value to the user's current browser session before redirecting to the identity provider and verifies that the returned state matches upon callback. Since the attacker cannot guess or forge the victim's session-specific state token, the application rejects the forged callback request.

# 2. Redirect URI Attacks
Validating a redirect_uri only by checking the root domain or allowing wildcard paths/subdomains creates a dangerous opening when paired with open redirects or user-controlled content on that domain. For example, suppose an application allows any path on [https://innovateinc.com/](https://innovateinc.com/)* as a valid redirect_uri, and the site also has an unvalidated redirect endpoint like [https://innovateinc.com/logout?next=https://evil.com](https://innovateinc.com/logout?next=https://evil.com) (or a subdomain takeover on old-blog.innovateinc.com). An attacker could craft a malicious authorization link setting redirect_uri=[https://innovateinc.com/logout?next=https://evil.com](https://innovateinc.com/logout?next=https://evil.com). Once the victim logs in at the identity provider, the provider sees a matching domain, approves the redirect, and appends the victim's secret authorization code to the URL—which [innovateinc.com/logout](https://innovateinc.com/logout) immediately forwards to evil.com (or leaks via the Referer header), allowing the attacker to steal the code and hijack the victim's account.

# 3. User Experience vs. Security
A major trade-off engineering teams face when adding "Login with Google" or GitHub is balancing frictionless onboarding against increased attack surface and trust dependencies. While third-party OAuth removes password fatigue and eliminates the risk of storing weak user passwords locally, it shifts security responsibility onto complex redirect handling, token storage, and account-linking logic. Furthermore, if an application automatically links an OAuth login to an existing local account solely by matching email addresses without verifying that the provider actually confirmed ownership of that email, an attacker could register a third-party account with a victim's email and take over their profile. Teams must weigh faster user sign-ups against the engineering discipline required to enforce strict exact-match redirect_uri allowlists, PKCE, state validation, and safe account linking.
